# AI 知识库搭建记录

## 1. 目标与架构

建立一套可持续沉淀 AI 相关知识的双轨结构：

```
WorkBuddy 资料库（日常编辑、语义检索、对话内问答）
        ↕ 同步
GitHub 仓库（标准 Markdown、版本管理、跨工具复用）
```

选择双轨而非单一存储的原因：

| 需求 | 资料库 | GitHub 仓库 |
| --- | --- | --- |
| 对话内语义检索 | ✅ 原生支持 | ❌ |
| 版本历史与差异对比 | ❌ | ✅ |
| 被其他 AI 工具读取（Cursor / Dify / RAGFlow） | ❌ 无开放 API | ✅ 标准 Markdown |
| 离线可用 | ⚠️ 依赖客户端 | ✅ 本地 clone |

## 2. 目录设计

按「知识生命周期」而非「工具名」分层，五个目录覆盖从模型认知到落地与合规的完整链路：

- `01-模型与能力`：模型清单、参数规格、能力边界、选型结论
- `02-提示词工程`：模板、少样本示例、调优记录、失败复盘
- `03-应用与工程`：RAG、Agent、微调等落地实践与部署配置
- `04-数据集与评测`：数据字典、清洗规则、指标定义、对比实验
- `05-政策与合规`：监管要求、内容安全、数据合规

设计约束：

1. 目录层数不超过一层子分类，避免检索时路径过深导致归类犹豫。
2. 同一主题优先扩充已有文档，不新建碎片文件。
3. 每篇文档头部统一标注主题、来源、整理日期、适用版本。

## 3. 自动归档机制

配置了每日 22:00 触发的定时任务，将当日对话中可复用的结论整理入对应目录。

规则要点：

- 只保留可复用结论、技术决策、方法步骤、踩坑根因、数据指标
- 不复述寒暄、过程性试错、临时状态
- 按主题自动分流，归档后更新索引文档
- 当日无有效内容则跳过，不产生空文档

## 4. 踩坑记录：GitHub 连接器权限

### 现象

| 操作 | 结果 |
| --- | --- |
| `get_me` 查询身份 | 成功，返回 `Merlin0207` |
| 读取公开仓库 `octocat/Hello-World` | 成功 |
| 读取自有私有仓库 `Merlin0207/ai-knowledge` | 404 |
| 通过接口创建仓库 | 403 `Resource not accessible by integration` |

### 根因

两点叠加：

1. 连接器使用受限范围的集成令牌，只覆盖公开仓库，不含私有仓库读写权限。
2. 该授权模式下，新建仓库不会自动纳入授权集合。GitHub 对无权限的私有仓库统一返回 404 而非 403，以避免泄露仓库存在性，因此「404」不能直接推断为「仓库不存在」。

### 排查方法

用公开仓库做对照实验，是区分「令牌失效」与「权限范围不足」最快的手段：

- 公开仓库能读 → 令牌有效，问题在范围
- 公开仓库也读不了 → 令牌本身失效

### 结论的修正

仓库改为 Public 后，**读取**立即恢复；但**写入**仍返回 `403 Resource not accessible by integration`。
说明集成令牌只有 `public_repo` 级别的读权限，不含 `repo` 写权限。

因此最终采用本地 Git 推送：仓库公开后，本地凭据管理器中的 GitHub 账号可直接 push，绕开连接器的写权限限制。

### 三种通道的适用范围

| 通道 | 读 | 写 | 适用场景 |
| --- | --- | --- | --- |
| 连接器（集成令牌） | ✅ 公开仓库 | ❌ 403 | 只做检索、核对远端文件 |
| 本地 Git + 凭据管理器 | ✅ | ✅ | 批量写入、提交历史完整 |
| fine-grained PAT | ✅ | ✅ | 需要私有仓库且要自动化时 |

### 「授权成功」不等于仓库可访问

实测中曾出现三件事同时成立，容易误判：

- 授权流程走完，界面显示已连接
- `get_me` 能返回正确账号名
- 目标仓库仍返回 404

判断顺序应为：先读一个公开仓库（如 `octocat/Hello-World`）→ 成功说明令牌有效，问题在**范围**；失败说明令牌**失效**。再用 `get_me` 核对账号是否与仓库 owner 一致（账号搞错也会 404）。

## 5. 踩坑记录：OAuth 授权页按钮点不动

**根因**：国内网络下 `github.githubassets.com`、`avatars.githubusercontent.com` 等 CDN 经常加载失败。页面 HTML 能显示，但 JavaScript 未执行，按钮「看得见、点不动」。

按键位现象分两类处理：

| 现象 | 根因 | 处理 |
| --- | --- | --- |
| 按钮灰色不可点、样式错乱（无图标） | CSS/JS 资源加载失败 | 见下「资源类」 |
| 按钮绿色可点、点击无反应或转圈 | 事件脚本被拦，或 OAuth `state` 过期 | 见下「脚本类」 |
| 页面无 Authorize 按钮，只有登录框 | 未登录或 2FA 未通过 | 先登录 |

资源类（按成本递增，前一步无效再下一步）：`Ctrl+Shift+R` 强制刷新 → 关闭浏览器增强安全模式 → 无痕窗口（同时排除广告拦截扩展）→ 手机热点验证是否链路问题 → DNS 改 `223.5.5.5` / `1.1.1.1` 后 `ipconfig /flushdns` → F12 Network 面板按状态列排序找失败域名。

脚本类：刷新页面重来（`state` 有效期短）→ 清 `github.com` 的 Cookie → 跟踪防护降为「基本」。

## 6. 踩坑记录：空仓库没有「Add file」按钮

空仓库（零提交）不显示文件列表，GitHub 给的是「快速设置」页，上传入口藏在页面中部的一段说明文字里（`…or uploading an existing file`）。

**直接路径**：`https://github.com/<owner>/<repo>/upload/main`（分支名不是 main 时换 `master`）。

兜底：先用「creating a new file」提交一个 `README.md`，仓库有了首个提交后，右上角的 Add file 就会正常出现。

上传注意：`.gitignore` 是隐藏文件，资源管理器需开启「显示隐藏的项目」；拖拽时保持目录层级，不要只拖文件夹内的文件。

## 7. 网页上传与本地提交的分叉处理

网页上传会在远端产生一个独立提交，与本地历史分叉，`git push` 会被拒绝。处理顺序：

```bash
git fetch origin
git merge origin/main --allow-unrelated-histories   # 允许无关历史合并
git push origin main
```

本例合并后唯一差异是远端缺 `.gitignore`，补齐即可。**不要用 `--force`**——会把网页端上传的内容冲掉。

## 8. 定时归档的双写机制

归档任务不能只写一处，否则两轨会漂移。当前配置：

| 步骤 | 目标 | 失败处理 |
| --- | --- | --- |
| 1 | 资料库对应主题目录（语义检索可用） | 记录失败原因，继续下一步 |
| 2 | 本地仓库同名 Markdown（版本管理） | 同上 |
| 3 | `GIT_TERMINAL_PROMPT=0 git push origin main` | 被拒先 `git pull --rebase`，仍失败只重试一次，然后明确报告失败原因 |

约束：`GIT_TERMINAL_PROMPT=0` 必须设置，否则在无人值守环境下 git 会等待凭据输入而挂起。

## 9. 仓库公开后的长期约束

仓库为 Public 后，任何人与爬虫都能读取、clone、被搜索引擎收录，且已扩散的内容无法收回。因此归档内容必须遵守「数据许可与内容合规红线」中的禁止项，尤其是**不得写入任何 API Key、token、客户信息与内部系统地址**。
