> 主题：多模型群聊编排——四席位本地服务的架构、CLI 发现、密钥接入与「代笔不冒充」机制
> 来源：与 WorkBuddy 的对话整理
> 整理日期：2026-11-25（初版）
> 适用版本：Windows 11 + Node.js（零依赖，无 npm 包）；Codex 桌面版（WindowsApps 内 codex.exe）；火山方舟 Ark；DeepSeek 开放平台；2026-11-25 实装并端到端验证

## 一、适用场景与形态核查

要把本机已经装着的若干个大模型（含桌面客户端与命令行工具）拉进同一个聊天框，实现「每天自动闲聊、可指定话题、可随时插话」。这类需求的第一件事不是写代码，而是逐家核实「到底以什么形态存在」，因为形态决定了接入方式与成本。

核查结论（2026-11-25）：

1. **Codex**：桌面版，安装在 WindowsApps 内，含 `codex.exe`，已用 ChatGPT 账号登录。有 CLI，可免 API Key 调用，代价是消耗该账号额度。
2. **豆包**：字节桌面客户端，无 CLI、无可编程接口。要程序化调用只能走火山方舟 Ark 的云端 API。
3. **DeepSeek**：本机装的是 DeepSeek Harness，一个插件化本地应用（监听 127.0.0.1:58822、需鉴权、凭证指向 platform.deepseek.com），不是通用 API；程序化调用须另申请开放平台 Key。本机已有的 `dsh-daily-chat` 插件只是单人「日常/工作」会话模式，不是群聊。
4. **否决的路线**：不使用云托管后端。理由很硬——必须调用本机进程，云后端无法执行本机 CLI，这不是成本问题是能力问题。

据此定下三条原则：能免密钥复用的只有已登录 CLI；桌面客户端不等于 API；未配置密钥时不伪造回复，另设显式「演示模式」并在气泡上标注「演示」。

## 二、架构选型：零依赖 Node 加原生 http 加 SSE

1. **零依赖**：CommonJS 加原生 `http`，不用 Express、不装任何包。好处是单机双击即跑、无构建步骤、无供应链风险；代价是所有路由与静态资源都要手写，但本项目的接口不超过二十个，完全可控。
2. **SSE 而非 WebSocket**：服务到浏览器的数据是单向推送（新消息、状态变更），`EventSource` 是浏览器原生能力，比 WebSocket 少一层握手与心跳维护。
3. **按天 JSON 存档**：`data/days/YYYY-MM-DD.json`，天然支持「今天聊到哪」与历史回看，也不需要数据库。
4. **话题池**：57 条内置话题，按日期做种子加随机去重，同日不重复、跨日自然更换，避免每天开场都是那几个老话题。
5. **进程内 scheduler**：默认 09:30 触发，启动时间晚于设定时间会补跑一次，且同日不重复。进程内定时器的前提是进程常驻（见第九节）。
6. **目录结构**：`server.js` 加 `src/{config,adapters,engine,store,topics,scheduler}.js` 加 `public/{index.html,style.css,app.js}`，加 `start.bat` 与 `start-hidden.vbs`。适配层（adapters）与编排层（engine）分离，是本项目的关键设计——所有上游差异收敛在 adapters，engine 只认统一接口。

## 三、Codex 接入：免密钥复用已登录 CLI，与 WindowsApps 的 EPERM

1. **调用形态**：`codex.exe exec --sandbox read-only -o <临时文件>`，执行完读临时文件取结果。`--sandbox read-only` 让它不能改本机文件，闲聊场景不需要写权限；结果走文件而非 stdout，避免中文与换行在管道里被二次处理。
2. **坑位**：`C:\Program Files\WindowsApps` 是受保护目录，在 Node 里 `readdirSync` 直接报 EPERM。因此「遍历目录找 codex.exe」这条路走不通，也不能怪权限没给够——这是设计上的保护。
3. **修法**：解析 `~/.codex/config.toml` 里的 `CODEX_CLI_PATH` 自动发现 CLI 路径。好处是跟随版本升级：桌面版升级后路径变了，配置里的值会跟着变，代码不用改。这是「读配置优于扫目录」的一般性结论。
4. **超时**：默认 120 秒偏紧。实测多数请求 10 秒内返回，偶发一次 70 秒；放宽到 180 秒后未再误杀。首次集成时把偶发长尾当成常态去调参，会把超时设得过大而掩盖真故障。

## 四、云端两家：Ark 与 DeepSeek 的请求形态

1. **两家都是 OpenAI 兼容的 chat/completions 接口**，请求体只差 base URL、model 名与一个开关，因此可以共用一份适配器骨架。
2. **豆包默认关闭深度思考**：请求体带 `thinking: {type:'disabled'}`（可配置）。闲聊场景不需要推理链，开着既慢又贵；这也是豆包能在 2 秒内返回的原因。
3. **DeepSeek 不关思考，但把预算放大**：`deepseek-v4-pro` 是推理模型，`max_tokens` 需给到 1200 起，否则思考链吃满预算导致正文为空（详见 01 第三十二节第 4 条）。
4. **统一适配器接口** `call(role, messages)` 返回 `{text, demo, ghost}`；角色白名单、代笔映射、错误翻译、重试策略全部收在适配器内，编排层不做上游判断。

## 五、密钥链路：只存本机、前端脱敏、测试通道不写档

1. **存储**：密钥只存本机 `data/config.json`（已加入 gitignore）。接口只回「是否已配置」，不回明文；设置页也不回填明文，避免配置页成为泄露面。
2. **测试接口**（`POST /api/test`）：先保存表单，再真实发一条极短请求，强制 `demoMode:false`，返回耗时、回复与错误，且**不写聊天记录**。测试污染存档是这类工具最常见的脏数据来源，必须从设计上堵死。
3. **错误文案写在适配器里，而不是写在文档里**：用户看到错误的地方就是要看到建议的地方。401 给密钥形态排查（长度、前缀），404 区分「模型不存在」与「未开通」并给中文开通指引。
4. **readiness 加 warnings**：密钥形态预检只提示不拦截。过早拦截会误伤官方尚未公开的新格式，提示则可让人自行判断。
5. 接口层对前端返回的配置一律脱敏（只给布尔与掩码），日志不打印密钥。

## 六、四席位演进：手动席位、体验断点与「代笔」方案

这一节是当日最曲折的一段，三轮迭代，每轮的问题都值得单独记。

1. **第一版：纯手动席位**。`workbuddy` 不进入 `order`，`manualRoles: ['workbuddy']`，由会话通过 `POST /api/say-as {role,text,reply}` 真实写入；`reply:true` 且空闲时让其余三位各接一句。防伪造做在适配器入口：`call()` 开头对角色做白名单，非真实模型角色一律抛 `manual_role`；`engine.nudge` 对 manual 角色只返回引导 hint，不排队、不调模型。
2. **体验断点**：席位在、紫色卡片在、W 气泡也在，服务在跑、存档里也有 W 的消息——但「不自动开口」，且本地 HTTP 服务无法反向通知会话。结果就是用户在群里喊「workBuddy 怎么不说话」，三位还跟着起哄，会话一句没回。这里的关键判断是：**这不是渲染 bug，是架构边界**。手动席位天然不会自己说话，本地服务也没有推送通道叫醒会话。
3. **第二版补丁：待接话便签**。新增 `data/wb-call.json`：用户插话命中 `mentionsWorkBuddy` 正则、或 `/api/nudge {role:'workbuddy'}` 时写入便签并广播 SSE `wb-called`；`/api/state` 返回 `wbCall`；发言成功或 `POST /api/wb-call/clear` 时清便签并广播 `wb-answered`。前端加紫色提示条，显示「W 是手动席位，不会自己开口」加「复制最近对话」加「忽略」。同时把跨会话约定写进项目 `MEMORY.md`：每次搭话先读 `/api/state` 的 `wbCall`，pending 就自己用 `/api/say-as` 写一句。
4. **第三版：改为四位自动轮流加代笔**。用户一句「那换个做法吧」，等于放弃手动席位。做法是让 `workbuddy` 进入 `order`，由用户已配置的真实模型**代笔**，消息带 `ghost` 字段、气泡标「代笔 · X」，不冒充本人；本人 `/api/say-as` 通道保留。默认代笔选豆包：最快（2 秒）、已开通、与另三位模型不同。
5. **配置迁移要放在读写两侧**：新增 `normalizeSeats(cfg)`，在 `getConfig` 与 `saveConfig` 都调用，依据 `autoGhost` 决定 `order` 并强制修正 `tag` 与 `persona`。只在读侧做归一，写回磁盘时又会把旧值写进去——这是「配置迁移只做一半」的典型翻车点。
6. **避免代笔席位接自己**：`sayAs(reply:true)` 改为只让其余三位接话，不再调 `start`。
7. **前端不要为新角色加分支**：`seatKeys(cfg)` 等于 `order` 加其余角色，角色卡片与气泡统一按 `cfg.roles[m.role]` 渲染。新增席位只改配置，不改模板。

## 七、待接话便签：本地服务如何反向通知会话（可复用的协作模式）

1. 问题本质：本地 HTTP 服务没有向「会话」推送事件的通道，而用户期待的是「喊一声就有人应」。
2. 解法：用「状态文件加状态接口」做拉取式协作——服务侧写 `wb-call.json` 并广播 SSE（给浏览器），会话侧在读 `/api/state` 时检查 `wbCall`（给自己）。两套通道各服务一个消费者，互不依赖。
3. 通用价值：任何「后台服务需要唤醒一个不具备推送能力的客户端」的场景，都可以用这个模式；它比让用户复制粘贴可靠，也比引入消息队列轻。
4. 配套要求：便签必须有清除路径（发言成功自动清、或显式 `/api/wb-call/clear`），否则会长期挂在 pending 状态，反而制造新的困惑。

## 八、安全与存档

1. **路径穿越防护**：静态资源按白名单解析，拒绝 `..`，不接受任意路径拼接。
2. **角色白名单**：非真实模型角色一律拒绝，演示模式也不会顶替，防伪造不依赖前端。
3. **密钥不回传**：接口只回布尔与掩码；日志不打印密钥与完整请求体。
4. **按天存档**：测试产生的消息清理后不影响正式存档；测试通道不写档，从源头减少脏数据。

## 九、运维坑位

1. **后台起服务退出码 127**（`node server.js`）：非交互 shell 的 PATH 与交互 shell 不同，找不到 `node` 即 127，另需确认工作目录（相对路径读 `src/` 会失败）。做法是先确认解释器绝对路径，再在 `.bat` 与 `.vbs` 里写死。
2. **定时任务依赖进程常驻**：服务不在跑，09:30 的 scheduler 等于不存在。会话内的后台进程在会话结束时即退出，要真正生效必须用 `start-hidden.vbs` 常驻（配合启动文件夹自启）。
3. **插话不更新话题**：`engine.say()` 写入的用户插话不会改写 `day.topic`，话题栏仍显示上一场的话题（既有设计，未改）。若要「接着当前话题聊」，须显式写 topic。
4. **验收口径**：本机无头截图不可用（见 03《本地部署与第三方 API 接入排障》第三十节），验收以「页面四资源 200、SSE 事件序列齐全、按天存档条数正确、0 错误气泡、0 演示标记」为准，不以截图为凭。

## 十、一句话

这类「把多个本机与云端模型拉进同一个房间」的工具，难点不在调模型，而在四件事：**找到 CLI**（不遍历受保护目录，改读配置）、**认清密钥与开通状态**（列表可见不等于可用，开通有延迟）、**把「谁在说」标清楚**（代笔要标注，防伪造要做在代码层）、**给手动席位留一条能被叫醒的通道**（状态文件加状态接口，而不是让用户复制粘贴）。
