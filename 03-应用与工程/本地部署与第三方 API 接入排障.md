# 本地部署与第三方 API 接入排障

## 一、开源项目本地起服务的标准步骤

以 `Renhuai123/ziwei-doushu` 为例（MIT 许可）：

| 项目 | 值 |
| --- | --- |
| 技术栈 | Next.js 16.3.8（Turbopack）+ React 19 + Tailwind + iztro 排盘库 |
| 依赖安装 | 183 个包，约 2 分钟 |
| 启动耗时 | 约 556ms |
| 访问地址 | `http://localhost:3000` |

排盘是纯本地计算（`iztro` 库），不联网、不需要任何 API Key。重建启动：

```bash
cd <项目目录>
npm run dev
```

**第一个必查项**：先读 `.env.example` 与 README 的「快速开始」。本例的 `.env.example` 里有一段关键注释——「开源版不含 `/api/interpret` 等后端接口，下面这组配置只在你自己实现了接口后才会用到」。这意味着**填了 Key 也不会生效**，问题不在配置而在代码缺失。这类「配置看起来没生效」的问题，先确认对端代码是否存在。

## 二、自实现 OpenAI 兼容接口

### 接口契约（由前端既有调用反推）

- `POST /api/interpret`，请求体 `{chart, messages}`
- 响应为 **SSE 流**，逐行 `data: {"delta":{"text":"..."}}`，以 `data: [DONE]` 结束
- `POST /api/heming`（合盘分析），格式相同

### 分层实现

| 文件 | 职责 |
| --- | --- |
| `lib/ai/chart-text.ts` | 命盘对象 → 结构化文本 |
| `lib/ai/provider.ts` | OpenAI 兼容流式客户端，一套配置通吃多家服务商 |
| `lib/ai/prompts.ts` | 系统提示词与输出规则 |
| `app/api/interpret/route.ts` | 问答接口，SSE 流式 |
| `app/api/heming/route.ts` | 合盘接口，同样流式 |

**关键设计**：provider 按 OpenAI 兼容协议实现一次，即可覆盖 DeepSeek、通义千问、智谱 GLM、Moonshot、Ollama、miMo 与任意自定义端点——切换只改环境变量（`AI_PROVIDER` + 对应 `*_API_KEY`）。这是接多家模型最省事的抽象层。

前端一行不改——它本来就在等这两个路由。

### 验证方式

不要「写完就交」。用本地 mock 模型服务跑通完整链路，确认 SSE 分块、`[DONE]` 结束符、提示词长度都正确，再切真实 API。验证用临时服务与测试文件事后清理。

## 三、踩坑：流式接口间歇性 `fetch failed`

**现象**：真实接口调用约 1/3 概率失败，4–11 秒后断开，报 `ECONNRESET`；同一台机器上 `curl` 一直成功。

**根因**：不是密钥、不是模型名、不是网络不通，而是**长连接被对端重置**；`curl` 与 Node 内置 `fetch` 的代理/连接行为不同（`curl` 走系统代理，Node fetch 默认不走），因此出现「命令行能通、代码不通」的分裂现象。

**修复策略（关键在约束条件）**：

- 只在**尚未吐出任何字符**时静默重试一次，用户无感知。
- 已经出字后断开**不重试**，直接提示中断——否则前端会出现两段重复内容。

改完后连续 3 次全部成功。这条约束比重试次数本身更重要：流式场景下的盲重试会把可诊断的错误变成内容错乱。

## 四、密钥与配置

- 密钥写入 `.env.local`，该文件已在 `.gitignore` 的 `.env*` 规则内，不会被提交，也不会进公开仓库。
- 通过对话传递密钥会使其进入对话记录与云端存档。**更稳妥的做法是本地手填**，只让工具负责重启与验证。
- 配置模板保留全部服务商注释，切换时只取消对应行，避免每次重写配置文件。

## 五、连接器能力边界：以百度网盘为例

连接器在界面上显示「已连接」，不代表本轮对话可调用——**可用工具清单在会话开始时生成**，之后接入的连接器要新开对话才生效。表现为「工具不存在」而非权限错误。

### 能做（六类）

浏览目录、文件名/语义检索（含文档正文与图片 OCR）、文件与配额信息、整理（新建/复制/移动/重命名）、生成带有效期与提取码的分享链接、写入（保存文本 ≤ 2 万字，或转存公开 URL）。

语义检索是价值最高的一项：可按画面内容、文档含义查找，不必依赖文件名。

### 不能做（四类，属平台接口限制，非配置问题）

| 做不到 | 原因 |
| --- | --- |
| 下载网盘文件到本机 | 工具集无下载接口 |
| 上传本机任意文件到网盘 | 仅支持文本内容或公开 URL 转存 |
| 删除网盘文件 | 无删除接口，只能客户端操作 |
| 直接发送文件给他人 | 只能生成链接，发送需人工完成 |

**推论**：「把这个文件夹备份到网盘」这类需求目前无法实现，不要承诺。合理的分工是：网盘存大文件与原始素材，Git 仓库存 Markdown，知识库做加工成品区。

## 六、资料库内容给其他 AI 工具使用的路径

资料库无对外开放 API，第三方工具无法直接读取。三条通道可用性递减：

| 通道 | 其他 AI 可用性 | 说明 |
| --- | --- | --- |
| 分享链接 | 有限 | 网页动态渲染、需登录，抓取通常失败 |
| 导出为文件 | 可以 | 文档导 Markdown、表格导 CSV、页面导 HTML |
| Git 仓库 | **最通用** | 任何支持 Git / 文件读取的工具都能接入 |

因此把 Git 仓库当**中转层**：

```
资料库（编辑、语义检索） → 导出/同步 → Git 仓库（标准 Markdown） → Cursor / Dify / RAGFlow / 自建服务
```

代码类工具直接 clone；RAG 平台导入 Markdown 文件夹；对话类工具上传单篇或整包。

## 七、第三方能力包（Skill / 插件）的取证式验收

新装组件不能靠 README 判断可用性。2026-11-02 对三款足球预测 Skill 做了同口径实测，三款全部在「宣称」与「实现」之间存在落差，但落差位置完全不同——这恰好构成一份可复用的验收清单。

### 三款实测结果

| 组件 | 代码真伪 | 开箱可用 | 真实缺陷 |
| --- | --- | --- | --- |
| 贝叶斯足球预测器 | **假** | 否 | 数据获取函数直接返回写死的 mock；赔率硬编码另一场比赛；比分预测是 if/else 四选一 |
| 足球量化分析引擎 | 真 | 否（对俱乐部赛） | 引擎算法真实，但数据只有 48 支国家队静态快照；三项概率权重和 ≠ 1；价值检测不分方向 |
| 聚合数据查询 | 真 | 缺 Key | 脚本为真实 HTTP 调用；但只覆盖赛程与积分榜，联赛表缺目标联赛 |

### 黑盒验真：恒定输出测试（最先做，成本最低）

**做法**：准备 3 组差异极大的输入（真实对阵 A、真实对阵 B、跨领域对阵 C），跑同一入口，对比输出。

**判据**：若三组输出的概率分布几乎相同（实测为 51.9 / 28.6 / 19.5，比分全部 2-1），则该组件不含信息通路，可以立即判定为无效，无需继续读代码。

这是性价比最高的一步：**一次调用即可否掉一个假组件**，而且不依赖任何领域知识。原理很朴素——任何真实的预测函数的输出必须随输入变化；输出恒定意味着输入未被使用。

**进阶**：同时变化「输入」与「可调参数」，若参数改变也不影响输出，说明参数是装饰性的。

### 白盒审计：六个必查点

在确认组件有真实计算后，逐项核对实现与声明是否一致：

| 检查点 | 症状 | 实测案例 |
| --- | --- | --- |
| **数据覆盖** | 库内实体数远小于使用场景 | 48 支国家队 → 俱乐部赛全部 fallback 到默认值，四场输出同一个数 |
| **静默 fallback** | 查不到数据时返回默认值而非报错 | 缺数据时输出 Elo 1500、xG 1.35/1.35，看起来像结论 |
| **概率归一性** | 三项概率和 ≠ 1 | 平局项额外加 `(1-|elo_exp-0.5|)*0.15`，权重和 1.11–1.15，实力越接近平局被抬得越多（实测 26.0%→28.5%） |
| **信号的符号** | 用绝对值判定「有价值」 | `abs(edge) >= 3` → 模型低于市场 5.1pp 也被标为机会，而那是反向信号 |
| **阈值是否扣成本** | 固定阈值忽略费率 | 一刀切 3pp，而 87% 返还率下真实保本门槛是 4.9 / 3.9 / 6.1pp |
| **依赖与运行环境** | 依赖未安装，import 即失败 | 依赖 numpy / requests，目标机器均未安装 |

其中「静默 fallback」是最危险的一类。它不会报错，只会给出一个格式正确、量级合理的数字，然后被下游当成结论使用。**验收标准应明确要求：数据缺失时必须 `ok=False`，禁止用默认值继续计算。**

### 三条通用判断原则

1. **输出对输入不敏感 = 无信息**，与代码是否优雅无关。
2. **算法正确 ≠ 可用**。数据覆盖不足的引擎，其正确性只存在于演示集的 48 个实体上；对本场景等价于零。
3. **净价值 = 覆盖面 × 数据时效 × 节省的时间 − 维护与误触发成本**。只覆盖流程里最轻的一步（如查积分榜）、却要占一个技能位并承担未知时效风险的组件，净价值可能为负，不值得接入。

### 包装层必须自包含

本次踩到的工程坑：为修补第三方引擎写了包装层 `engine_patched.py`（不改上游原文件，避免升级覆盖）。三方组件被卸载后，上游文件一并消失，包装层随即失效。

**规则**：补丁/包装层若要长期可用，必须把被修补的核心逻辑**复制**进自身，只在文档里注明来源与版本，而不是 `import` 上游模块。两者是「fork」与「依赖」的区别——依赖会对上游的删除与升级做出承诺，fork 不会。

副本的成本是同步负担，依赖的成本是随时失效。对于不会频繁变动的算法核心，fork 几乎总是更优选择。

### 停用与卸载的差别

发现组件不可用后，关闭与卸载要分清：

- **关闭（disable）**：只是不进自动触发列表，文件仍在磁盘，可能被再次启用。
- **卸载（uninstall）**：文件删除，但依赖它的本地脚本会一起失效。

若本地已有代码引用了该组件，卸载前先把需要的逻辑 fork 出来。本次就是先写完自包含版本、再确认卸载。

## 九、API key 的安全传递：剪贴板通道

- **key 贴进聊天 = 留档**：会进入对话记录与云端存档，应视为已泄露，作废重开。
- **固化流程**：用户复制 key → agent 读剪贴板落盘（`deepseek.key`）→ 日志只显示脱敏特征（长度 + 前后各几位，如 `sk-615…5200`）→ 连通性自检。
- 落盘文件不进 Git（.gitignore 覆盖）。换 key 重复同一流程，余额跟账号走，不丢钱。

## 十、通道故障甄别：先探针，再排查脚本

Codex MCP 通道整体报错（传输中断）时，先用一个**最简单的联网探针任务**测试通道（如让它抓一个已知 URL），探针也超时 → 是 chatgpt.com 服务端故障，不是本地脚本问题。

**规则**：服务端整体故障时记录在案、等恢复后补跑，**不要反复重试本地脚本**——重试只能证明通道不通，不能修复它。恢复后先补跑被中断的任务（本次补上了马竞场的 codex 事实核验），再继续新任务。

## 十一、无头浏览器截图的 DPI 换算陷阱

### 现象

Edge（系统 125% DPI 缩放）+ headless Chrome 截图：页面右侧被稳定裁切，反复改 CSS 无效——**页面本身没有问题**。

### 根因（三个宽度互不相等）

- `--window-size=380` 在 125% DPI 下实际渲染 CSS 视口约 492（系数 k≈1.295）；
- PNG 宽 = window-size × force（`--force-device-scale-factor`）；
- 渲染内容宽 = innerW × force，而 innerW = window-size × k。

`--force-device-scale-factor=1` **不能**消除 window-size 与 CSS 视口之间的换算差，只影响输出像素密度。

### 解法（按优先级）

1. **别纠结 innerW，让内容左对齐占满 window**：内容居中时，视口比 window 宽 23%，右侧内容必然落在 PNG 之外。截图场景去掉居中样式即可，响应式布局交给 CSS。
2. **自动校准截图脚本**：先注入 JS 测 `innerWidth` 算出换算系数，再按系数反推 `--window-size`，一劳永逸。
3. **高清输出用大 force**：`force=3` 时 PNG 宽 = window × 3（如 400 → 1200px），文字锐利。

### 元教训

截图异常先区分「页面真溢出」与「截图工具链换算误差」：注入调试脚本量 `innerWidth`、对比 PNG 真实宽度，一次定位；反复改 CSS 是在解一个不存在的问题。布局验证的稳妥路径是**大视口居中截图**（HTML 本身是交付物、手机端由响应式 CSS 保证），不必强求小视口截图完美。
