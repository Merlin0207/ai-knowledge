## 二、自实现 OpenAI 兼容接口

### 接口契约（由前端既有调用反推）

- `POST /api/interpret`，请求体 `{chart, messages}`
- 响应为 **SSE 流**，逐行 `data: {"delta":{"text":"..."}}`，以 `data: [DONE]` 结束
- `POST /api/heming`（合盘分析），格式相同

### 分层实现

| 文件 | 职责 |
| --- | --- |
| `lib/ai/chart-text.ts` | 命盘对象 → 结构化文本 |
| `lib/ai/provider.ts` | OpenAI 兼容流式客户端，一套配置通吃多家服务商 |
| `lib/ai/prompts.ts` | 系统提示词与输出规则 |
| `app/api/interpret/route.ts` | 问答接口，SSE 流式 |
| `app/api/heming/route.ts` | 合盘接口，同样流式 |

**关键设计**：provider 按 OpenAI 兼容协议实现一次，即可覆盖 DeepSeek、通义千问、智谱 GLM、Moonshot、Ollama、miMo 与任意自定义端点——切换只改环境变量（`AI_PROVIDER` + 对应 `*_API_KEY`）。这是接多家模型最省事的抽象层。

前端一行不改——它本来就在等这两个路由。

### 验证方式

不要「写完就交」。用本地 mock 模型服务跑通完整链路，确认 SSE 分块、`[DONE]` 结束符、提示词长度都正确，再切真实 API。验证用临时服务与测试文件事后清理。

## 三、踩坑：流式接口间歇性 `fetch failed`

**现象**：真实接口调用约 1/3 概率失败，4–11 秒后断开，报 `ECONNRESET`；同一台机器上 `curl` 一直成功。

**根因**：不是密钥、不是模型名、不是网络不通，而是**长连接被对端重置**；`curl` 与 Node 内置 `fetch` 的代理/连接行为不同（`curl` 走系统代理，Node fetch 默认不走），因此出现「命令行能通、代码不通」的分裂现象。

**修复策略（关键在约束条件）**：

- 只在**尚未吐出任何字符**时静默重试一次，用户无感知。
- 已经出字后断开**不重试**，直接提示中断——否则前端会出现两段重复内容。

改完后连续 3 次全部成功。这条约束比重试次数本身更重要：流式场景下的盲重试会把可诊断的错误变成内容错乱。

## 四、密钥与配置

- 密钥写入 `.env.local`，该文件已在 `.gitignore` 的 `.env*` 规则内，不会被提交，也不会进公开仓库。
- 通过对话传递密钥会使其进入对话记录与云端存档。**更稳妥的做法是本地手填**，只让工具负责重启与验证。
- 配置模板保留全部服务商注释，切换时只取消对应行，避免每次重写配置文件。

## 五、连接器能力边界：以百度网盘为例

连接器在界面上显示「已连接」，不代表本轮对话可调用——**可用工具清单在会话开始时生成**，之后接入的连接器要新开对话才生效。表现为「工具不存在」而非权限错误。

### 能做（六类）

浏览目录、文件名/语义检索（含文档正文与图片 OCR）、文件与配额信息、整理（新建/复制/移动/重命名）、生成带有效期与提取码的分享链接、写入（保存文本 ≤ 2 万字，或转存公开 URL）。

语义检索是价值最高的一项：可按画面内容、文档含义查找，不必依赖文件名。

### 不能做（四类，属平台接口限制，非配置问题）

| 做不到 | 原因 |
| --- | --- |
| 下载网盘文件到本机 | 工具集无下载接口 |
| 上传本机任意文件到网盘 | 仅支持文本内容或公开 URL 转存 |
| 删除网盘文件 | 无删除接口，只能客户端操作 |
| 直接发送文件给他人 | 只能生成链接，发送需人工完成 |

**推论**：「把这个文件夹备份到网盘」这类需求目前无法实现，不要承诺。合理的分工是：网盘存大文件与原始素材，Git 仓库存 Markdown，知识库做加工成品区。

## 六、资料库内容给其他 AI 工具使用的路径

资料库无对外开放 API，第三方工具无法直接读取。三条通道可用性递减：

| 通道 | 其他 AI 可用性 | 说明 |
| --- | --- | --- |
| 分享链接 | 有限 | 网页动态渲染、需登录，抓取通常失败 |
| 导出为文件 | 可以 | 文档导 Markdown、表格导 CSV、页面导 HTML |
| Git 仓库 | **最通用** | 任何支持 Git / 文件读取的工具都能接入 |

因此把 Git 仓库当**中转层**：

```
资料库（编辑、语义检索） → 导出/同步 → Git 仓库（标准 Markdown） → Cursor / Dify / RAGFlow / 自建服务
```

代码类工具直接 clone；RAG 平台导入 Markdown 文件夹；对话类工具上传单篇或整包。

## 七、第三方能力包（Skill / 插件）的取证式验收

新装组件不能靠 README 判断可用性。2026-11-02 对三款足球预测 Skill 做了同口径实测，三款全部在「宣称」与「实现」之间存在落差，但落差位置完全不同——这恰好构成一份可复用的验收清单。

### 三款实测结果

| 组件 | 代码真伪 | 开箱可用 | 真实缺陷 |
| --- | --- | --- | --- |
| 贝叶斯足球预测器 | **假** | 否 | 数据获取函数直接返回写死的 mock；赔率硬编码另一场比赛；比分预测是 if/else 四选一 |
| 足球量化分析引擎 | 真 | 否（对俱乐部赛） | 引擎算法真实，但数据只有 48 支国家队静态快照；三项概率权重和 ≠ 1；价值检测不分方向 |
| 聚合数据查询 | 真 | 缺 Key | 脚本为真实 HTTP 调用；但只覆盖赛程与积分榜，联赛表缺目标联赛 |

### 黑盒验真：恒定输出测试（最先做，成本最低）

**做法**：准备 3 组差异极大的输入（真实对阵 A、真实对阵 B、跨领域对阵 C），跑同一入口，对比输出。

**判据**：若三组输出的概率分布几乎相同（实测为 51.9 / 28.6 / 19.5，比分全部 2-1），则该组件不含信息通路，可以立即判定为无效，无需继续读代码。

这是性价比最高的一步：**一次调用即可否掉一个假组件**，而且不依赖任何领域知识。原理很朴素——任何真实的预测函数的输出必须随输入变化；输出恒定意味着输入未被使用。

**进阶**：同时变化「输入」与「可调参数」，若参数改变也不影响输出，说明参数是装饰性的。

### 白盒审计：六个必查点

在确认组件有真实计算后，逐项核对实现与声明是否一致：

| 检查点 | 症状 | 实测案例 |
| --- | --- | --- |
| **数据覆盖** | 库内实体数远小于使用场景 | 48 支国家队 → 俱乐部赛全部 fallback 到默认值，四场输出同一个数 |
| **静默 fallback** | 查不到数据时返回默认值而非报错 | 缺数据时输出 Elo 1500、xG 1.35/1.35，看起来像结论 |
| **概率归一性** | 三项概率和 ≠ 1 | 平局项额外加 \\\\\\\`(1- |
| **信号的符号** | 用绝对值判定「有价值」 | `abs(edge) >= 3` → 模型低于市场 5.1pp 也被标为机会，而那是反向信号 |
| **阈值是否扣成本** | 固定阈值忽略费率 | 一刀切 3pp，而 87% 返还率下真实保本门槛是 4.9 / 3.9 / 6.1pp |
| **依赖与运行环境** | 依赖未安装，import 即失败 | 依赖 numpy / requests，目标机器均未安装 |

其中「静默 fallback」是最危险的一类。它不会报错，只会给出一个格式正确、量级合理的数字，然后被下游当成结论使用。**验收标准应明确要求：数据缺失时必须 **`ok=False`**，禁止用默认值继续计算。**

### 三条通用判断原则

1. **输出对输入不敏感 = 无信息**，与代码是否优雅无关。
2. **算法正确 ≠ 可用**。数据覆盖不足的引擎，其正确性只存在于演示集的 48 个实体上；对本场景等价于零。
3. **净价值 = 覆盖面 × 数据时效 × 节省的时间 − 维护与误触发成本**。只覆盖流程里最轻的一步（如查积分榜）、却要占一个技能位并承担未知时效风险的组件，净价值可能为负，不值得接入。

### 包装层必须自包含

本次踩到的工程坑：为修补第三方引擎写了包装层 `engine_patched.py`（不改上游原文件，避免升级覆盖）。三方组件被卸载后，上游文件一并消失，包装层随即失效。

**规则**：补丁/包装层若要长期可用，必须把被修补的核心逻辑**复制**进自身，只在文档里注明来源与版本，而不是 `import` 上游模块。两者是「fork」与「依赖」的区别——依赖会对上游的删除与升级做出承诺，fork 不会。

副本的成本是同步负担，依赖的成本是随时失效。对于不会频繁变动的算法核心，fork 几乎总是更优选择。

### 停用与卸载的差别

发现组件不可用后，关闭与卸载要分清：

- **关闭（disable）**：只是不进自动触发列表，文件仍在磁盘，可能被再次启用。
- **卸载（uninstall）**：文件删除，但依赖它的本地脚本会一起失效。

若本地已有代码引用了该组件，卸载前先把需要的逻辑 fork 出来。本次就是先写完自包含版本、再确认卸载。

## 十、通道故障甄别：先探针，再排查脚本

Codex MCP 通道整体报错（传输中断）时，先用一个**最简单的联网探针任务**测试通道（如让它抓一个已知 URL），探针也超时 → 是 chatgpt.com 服务端故障，不是本地脚本问题。

## 十一、无头浏览器截图的 DPI 换算陷阱

### 现象

Edge（系统 125% DPI 缩放）+ headless Chrome 截图：页面右侧被稳定裁切，反复改 CSS 无效——**页面本身没有问题**。

### 根因（三个宽度互不相等）

- `--window-size=380` 在 125% DPI 下实际渲染 CSS 视口约 492（系数 k≈1.295）；
- PNG 宽 = window-size × force（`--force-device-scale-factor`）；
- 渲染内容宽 = innerW × force，而 innerW = window-size × k。

`--force-device-scale-factor=1` **不能**消除 window-size 与 CSS 视口之间的换算差，只影响输出像素密度。

### 解法（按优先级）

1. **别纠结 innerW，让内容左对齐占满 window**：内容居中时，视口比 window 宽 23%，右侧内容必然落在 PNG 之外。截图场景去掉居中样式即可，响应式布局交给 CSS。
2. **自动校准截图脚本**：先注入 JS 测 `innerWidth` 算出换算系数，再按系数反推 `--window-size`，一劳永逸。
3. **高清输出用大 force**：`force=3` 时 PNG 宽 = window × 3（如 400 → 1200px），文字锐利。

### 元教训

截图异常先区分「页面真溢出」与「截图工具链换算误差」：注入调试脚本量 `innerWidth`、对比 PNG 真实宽度，一次定位；反复改 CSS 是在解一个不存在的问题。布局验证的稳妥路径是**大视口居中截图**（HTML 本身是交付物、手机端由响应式 CSS 保证），不必强求小视口截图完美。

## 十二、多 agent 并发写库的数据覆盖事故（2026-11-04 新增）

**现象**：11-04 清晨回填时发现马竞 vs 拜仁一场的 forecasts 缺失、无法计算 Brier。根因：前一晚为该场补跑 codex 时，import 操作清空了该场的预测记录——多 agent 流程先后写同一数据文件，后一次全量导入覆盖了前一次。

**处置**：按原值恢复该场五行预测记录并重算总账。

**规则**：

1. 多 agent（主模型 + codex + deepseek）先后写同一个数据文件（predictions.db / forecasts 表）时，任何全量导入（import）前必须先备份；
2. import 后立即校验行数与预期一致，不等次日回填才发现；
3. 回填脚本应把「某场 forecasts 缺失」当一等告警显式报出，而不是静默跳过——缺失静默，账目就会在无人察觉时失真。

## 十三、模板渲染与数据写入的四类静默失败（2026-11-05 新增）

同一时段内出海报与写核销记录，连踩四处。共同特征：**不报错、只出错**——脚本退出码 0，产物却是坏的。这类问题比抛异常的 bug 更贵，因为没有任何信号提示你去检查。

### 1. 撇号截断内联脚本

**现象**：赛果备注要写「尼奥尼 25'」，`'` 直接闭合了 Python 字符串字面量，其后的中文被当作代码解析，写入内容在分钟数处截断，后续字段全部丢失。

**规则**：任何含用户原文、赛事比分、人名备注的写入，**一律先落成 **`.py`** 文件再执行，不用 **`python -c`** 内联**。若必须内联，用三引号并检查原文中的整族引号（`'` `’` `"` `"`）。

### 2. CSS 的 `%` 与 Python 格式化符冲突

**现象**：海报模板用 `%` 做字符串插值，CSS 里的 `width: 100%` 被当成格式符解析，抛 `unsupported format character` 或静默输出错位。

**规则**：**HTML/CSS 模板不要用 **`%`** 或 **`.format()`** 插值，改用 token 占位（**`{{TITLE}}`**）+ **`str.replace`** 一次性替换**。凡目标产物本身是一个表达式语言（CSS、LaTeX、Jinja 片段、SQL），插值方式必须先确认转义边界，再写模板。

### 3. 深底上的深色元素不可见

**现象**：比分分隔符取了球队主色（深红），压在深色背景上，「2–3」整段不可读，第一版直接作废。

**规则**：**对比度按背景判定，不按品牌色判定**。深色底上的装饰性字符一律用半透明白（`rgba(255,255,255,.85)`）；主色只用于大面积色块或浅底文字。出图前固定做一次自检：缩到 30% 尺寸看关键信息是否仍可辨认。

### 4. 队徽/图标 ID 必须逐图肉眼核验

**现象**：按名称检索到的队徽 ID 存在错配（同名俱乐部、二队、历史队徽、女队）。

**规则**：批量下载后**逐张打开确认图形**，不信任接口返回的名称匹配。本次核验正确的 ID：曼城 50、莱比锡 173、埃因霍温 197、布鲁日 569。此项已固化为固定步骤，不因「上次对过」而跳过——素材源会更新，上次正确不保证这次正确。

### 5. 附：敏感性扫描基准 bug 的回归

11-03 已修复的「`dd=0` 时丢失基准差、退化为等强对称」在 11-05 建模中**再次出现**，同一现象、同一位置。

说明此前的修复是就地改了一个值，而不是加了约束。

**规则**：修此类数值 bug 时同步写入断言（如 `assert abs(base_diff) > eps or is_symmetric_input`），并在脚本入口维护一组固定回归用例。**没有断言的修复等于没有修复**——它只对当下的输入成立，重构即复发。

### 元教训

四类失败共享一个结构：**格式化/编码/视觉层面的错误不触发执行层异常**。对应的通用防线不是更小心的编码，而是「产物级校验」：写入后回读校验字段数、模板渲染后断言无残留占位符、出图后降采样目视。把校验点放在产物上，而不是放在代码上。

## 十四、seed 字段键名错误导致的静默落库失败（2026-11-08 新增）

### 现象

回填 6 场赛果时，`import` 返回成功、比赛与概率全部入库，但\\\*\\\*比分预测（score\\\\\\\_\\\*\\\***forecasts）一条未进**。全程无报错、无警告。

### 定位

不做逻辑猜测，直接查 import 对 `scores` 字段的预期格式，发现 seed 中键名写成了 `list`，schema 要求为 `items`。字段名不符时该字段被静默丢弃，其余字段照常写入。

### 修复

按 λ + 0.4 校准后的比分布重新计算，用 SQL 直插补齐 `score_forecasts`，核销数据恢复完整。

### 归类与判据

这是当日第三例同类故障，三例共同点已可归纳为一条工程结论：

| 案例 | 触发方式 | 表现 |
| --- | --- | --- |
| 11-04 马竞场 forecasts 被 codex 补跑清空 | `import` 全量覆盖 | 已有预测行消失 |
| 11-05 模板渲染静默失败 | 占位符与格式化语法冲突 | 输出为空但退出码 0 |
| 11-08 比分未入库 | 字段键名错误 | 字段被丢弃，其余正常 |

> **判据：**`pred.py import`\\\*\\\* 是「全量覆盖式 + 容忍缺字段」的写入，任何键名错误或字段缺失都不报错。\\\*\\\*

因此对应三条操作纪律：

1. `seed` 结构以 schema 为准，不靠「上次这样能跑」；
2. 静默失败优先查**字段名/键名**，再查逻辑；
3. `import` 后必须回读校验条数（`brief` 或 `show`），确认每一类子表都写进去了，而不是只看 import 的返回。

第三点是把「静默失败」变成「可发现失败」的唯一低成本手段——**没有回读校验的写入，等于没有写完。**

## 十五、盘口符号口径反转导致的批量错判（2026-11-09 新增）

### 现象

11-09 凌晨核销曼联 4-4 维拉时，让球盘判定与现实全部对不上：按库内记录计算为「4 场 1 对 1 走 2 错」，但逐场对照亚盘结果后明显不符。

### 定位

**根因**：11-08 那批 seed 的让球字段用了「**负 = 主让**」，而库内既有口径是「**正 = 让球**」。四场 seed 同源同批，因此四场全错，且错误方向一致（符号翻转），核销时表现为「判定与现实系统性镜像相反」。

**影响面核对方法（必做）**：不能只修发现的那几行，必须**全量复核历史记录**。本次复核 44 条让球记录：40 条口径正确，4 条错——错的全是同批 seed，其余历史数据未受污染。这一步把「局部污染」与「口径整体作废」区分开，决定了修复成本。

### 修复与修正后的成绩

4 行符号翻转后逐场对照：桑德兰**让胜 ✓**、伊普斯**走水**、那不勒斯**让负 ✓**、曼联**让负 ✓**——全部与现实一致，反证符号修正是对的。

对外报出的让球成绩由「1 对 1 走 2 错」修正为 **3 对 1 走**。此处有一条纪律：**已对外报出的成绩在修正前一律视为待核**，宁可晚报，不可带着错口径报。

### 程序化防线（真正的修复）

符号错误的特点是「能算通、算得反」——数值合法、概率和为 1、不报任何错。因此防线只能建在入库口，`pred.py` 导入时强制两件事：

1. **三项概率和校验**（1X2 必须归一到 1，容差内才算通过）；
2. **中文回显确认**：导入时打印「主队让 1 球」这类人类可读语句，由人肉眼确认与 seed 意图一致，口径不明即拒绝入库。

> **判据：符号 / 正负方向类错误无法用类型系统或断言发现，唯一有效防线是「人类可读回显」——把机器理解的语义翻译回自然语言，让人看一眼。**

### 与前一节（seed 键名错误）的同族关系

| 案例 | 错误类型 | 表现 | 防线 |
| --- | --- | --- | --- |
| 11-08 比分未入库 | 键名错（`list` vs `items`） | 字段被静默丢弃 | schema 先行 + 回读校验 |
| 11-09 让球全错 | 符号约定反转 | 数值合法、语义镜像 | 中文回显 + 概率和校验 |

两例共同点：**导入接口对内容零校验**。凡是「容忍缺字段、容忍任意数值」的写入接口，都必须在外层补语义校验，否则错误只能在核销时暴露——而核销时错误已经变成了错误结论。

### 可复用清单

1. 让球类字段必须显式声明符号约定（正 = 让球 / 负 = 受让），并写进 seed schema 注释；
2. 每批 seed 导入后，先抽 1–2 场做「现实对照」（用已知赛果的旧场次试算），再批量入库；
3. 修正历史数据后，必须重算全部相关成绩，并显式声明「此前报出的数字作废」；
4. 跨批次复用 seed 模板时，符号与键名是最容易继承错的两处——模板要带注释，不能只有结构。

## 十六、无音轨短视频转文案：字幕 OCR 通道（2026-11-11 新增）

### 现象与判据

抖音下载的 mp4（115 MB，4 分 48 秒）走 `AudioTranscribe` 报 `Invalid audio file`。**不要重试转录**，先验证是否存在音轨：直接读前 1 MB 解析 mp4 原子结构，搜 `ftyp / moov / trak / mp4a / avc1 / aac`。本例只有 `ftyp, moov, trak, avc1`，无 `mp4a / aac / opus` → 确证无音轨。

环境里没有 `ffprobe` / `ffmpeg`（`command not found`），不要在探测链上耗时间；纯 Python 读 atom 就足够定性。

### 通道：抽帧 → 字幕带裁剪 → 长图拼接 → 逐图 OCR

```python
cap = cv2.VideoCapture(path)
cap.set(cv2.CAP_PROP_POS_MSEC, t * 1000)        # 按毫秒定位，每 11-12 秒一帧，首尾加密
band = fr[int(h*0.84):int(h*0.99), int(w*0.05):int(w*0.95)]   # 字幕带：底部 84%-99%，左右内缩 5%
canvas = Image.new('RGB', (900, len(grp)*100))  # 每 1.5 秒一条字幕，30 条纵向拼一张长图
```

本例产出：31 帧（拼 8 张四联图，用于快速看版式与判断有无音轨）+ 192 条字幕条（拼 7 张长图，逐图按顺序读即得全文）。

### 关键踩坑：cv2 不认 git-bash 的 `/tmp`

`cv2.imwrite('/tmp/vframes/f.jpg', frame)` **静默失败**——不抛异常、返回 False，`ls /tmp/vframes` 为空，连带 PIL 的 glob 也拿到空列表，表现为「抽了 28 帧但一张都没有」。
规则：Windows 上给 cv2 / PIL 的路径一律用原生绝对路径（`C:\Users\...\AppData\Local\Temp\...`），不要用 MSYS 风格路径；批量写图后必须 `ls` 点数验证，不要以「无异常」代替「有产出」。

### 产能与边界

- 4 分 48 秒视频 ≈ 7 张长图 OCR，约 3 分钟取全文；
- 无音轨 + 硬字幕的短视频，**字幕 OCR 比 ASR 稳定**；有音轨时仍优先 ASR（成本低一个量级）；
- OCR 结果是近似原文，专有名词、比分、数字必须回看原帧核对。

## 十七、预存在文件写入被拒的三层根因：编码 → ACL → 句柄锁（2026-11-11 新增）

### 现象

写回一个已存在的 CSV（736 字节，UTF-8-SIG + CRLF）全部失败：

- `open(path, 'w')` → `PermissionError [Errno 13]`；
- Write 工具 → `EBUSY: resource busy or locked`；
- `os.replace` / `File.Replace` / `Copy-Item -Force` → `WinError 5 拒绝访问` 或「正由另一进程使用」。

### 定位顺序（按此顺序最省时间）

| 步 | 检查 | 结果 | 结论 |
| --- | --- | --- | --- |
| 1 | 文件是否只读 | `IsReadOnly=False`，`mode 0666` | 排除只读属性 |
| 2 | BOM / 换行 / 编码 | UTF-8-SIG + CRLF 正常 | 排除编码 |
| 3 | **同目录新建文件能否写** | 新建 + 删除 OK | 排除目录级只读 → 问题在文件本身 |
| 4 | 同目录新文件能否覆盖 | 覆盖 OK | 排除「禁止覆盖」策略 |
| 5 | ACL | `CodexSandboxUsers: ReadAndExecute`；`16974 / SYSTEM / Administrators: FullControl` | 沙箱用户无写权限 |
| 6 | 换 PowerShell（真实用户身份，`whoami` 确认 `merlinlee\16974`） | 仍失败，报「正由另一进程使用」 | **真实根因是句柄锁**，ACL 只是叠加因素 |
| 7 | Restart Manager 定位持有者 | `RmGetList` 返回 `editor_sdk.exe` | 文件正在本地 Office 编辑器里打开 |

### 定位句柄持有者的可用手段（Windows）

- `handle.exe` / `handle64.exe`：默认未安装，不要指望；
- `openfiles /query`：需开启系统全局「维护对象列表」标志，非管理员被拒（`错误: 拒绝访问`）；
- **Restart Manager API（**`rstrtmgr.dll`**）**：无需额外工具，`RmStartSession → RmRegisterResources → RmGetList` 直接拿到 PID 与进程名，是本次唯一有效路径，ctypes 版本可内联跑。

### 正确处置

不要绕过锁——`Copy-Item` / `Move-Item` / 原子替换只会换一种错误码。`editor_sdk.exe` 持有意味着文件**正在 WorkBuddy 的本地 Office 编辑器里打开**，正确路径是走 `workbuddy-office-routing` → 本地 office 编辑（editor\_sdk 直接改已打开的文档并保存），而不是从外部进程覆盖磁盘文件。

### 可复用判据

1. 只有「某个预存在文件」写不了、同目录新建文件正常 → 文件级 ACL 或句柄，不是目录权限；
2. `EBUSY` / 「正由另一进程使用」→ 句柄锁，改权限无用；
3. 判定「沙箱 ACL 还是句柄」的分水岭：**换真实用户身份后仍失败 = 句柄**；
4. 见到 `editor_sdk.exe` 持有 → 立刻转本地 office 编辑通道，停止尝试替换。

## 十八、上游 500「首 token 超时」的处置（2026-11-11 新增）

**现象**：同一句提问首次返回 `500 first token timeout: no content within 150000ms`（附 traceid），原样重发即正常返回。

**判据**：错误文本含 `first token timeout` + 具体毫秒阈值 → 上游排队或推理超时，**与 prompt 长度、内容、工具配置无关**。

**处置**：原样重发一次；不要改写 prompt、不要降级模型、不要拆问题。重发仍失败才按通道故障排查（第十节「先探针，再排查脚本」）。

**代价意识**：单次超时的墙钟成本是 150 秒，串行任务里足以吞掉一个自动化窗口；长链路任务的关键路径上应保留可重入的中断点，避免一次超时导致整轮白跑。

## 十九、automation_update 短 ID 失效与 heredoc 撇号转义（2026-11-13 新增）

### automation_update 删除任务必须用完整 UUID

用前 8 位短 ID（如 `d680cd7f`）调用删除，工具返回成功但任务仍在列表里——删除实际未生效。修复：改用完整 UUID 删除两个过期任务，删除后回查列表确认。

**规则**：automation_update 的 id 字段一律传完整 UUID；任何删除/修改操作之后必须回查列表验证生效。

### heredoc 内嵌 Python 的撇号转义

单引号字符串内含撇号（如 `20\'`，球员译名场景常见）触发 SyntaxError。修复：含撇号的文本一律用双引号字符串包裹；生成 heredoc 脚本前先扫一遍待写内容里有没有 `'`。
