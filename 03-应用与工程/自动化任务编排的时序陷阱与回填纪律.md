# 自动化任务编排的时序陷阱与回填纪律

## 结论摘要

1. **一次性定时任务可能在计划时间之前触发。** 实测提前量约 10 小时，且触发时比赛尚未开球。
2. **跨时区的「凌晨场次」是最高危场景**：北京 01:30–04:00 的比赛，对应欧洲当地前一日晚间。在国内当晚设触发点必然扑空。
3. **扑空时的正确动作是「什么都不做」**：不写库、不导出、不生成结论。宁可空跑一次，也不要写进一条错数据。
4. **搜索结果里最容易混淆的不是「没有结果」，而是「往季同对阵的旧战报」。** 判据必须是「该源是否标注了本场日期/开赛状态」，而不是「有没有找到比分」。

## 一、事故经过

| 项 | 值 |
| --- | --- |
| 任务 | 四场凌晨赛事·赛果抓取回填 |
| 计划触发 | 2026-11-03 06:10（北京时间） |
| 实际触发 | 2026-11-02 20:09（北京时间） |
| 偏差 | 提前约 10 小时 |
| 后果 | 四场比赛均未开球；未执行任何写库操作 |

## 二、为什么「凌晨场次」是陷阱

赛事库里的 `kickoff` 字段存的是**北京时间**，但比赛实际发生在欧洲当地。两者相差 6–8 小时，且「北京日期」比「当地日期」早一天。

| 场次 | 北京时间 | 欧洲当地 |
| --- | --- | --- |
| 萨索洛 vs 佛罗伦萨 | 11-03 01:30 | 11-02 18:30 CET |
| 亚特兰大 vs 帕尔马 | 11-03 03:45 | 11-02 20:45 CET |
| 纽卡斯尔 vs 埃弗顿 | 11-03 04:00 | 11-02 20:00 GMT |
| 拉科鲁尼亚 vs 奥萨苏纳 | 11-03 04:00 | 11-02 21:00 CET |

**推论**：只要触发时间落在「北京时间 11-02 晚间」，这四场就一场都没开。而任务名里写的是「11-03 凌晨」，容易让人以为「11-02 晚上已经打完了」。

### 可复用的排期规则

| 场景 | 触发点规则 |
| --- | --- |
| 北京凌晨（00:00–06:00）开球的海外赛事 | 回填触发点必须 ≥ 北京时间 06:00（末场结束后留 1.5–2h 缓冲） |
| 北京时间白天/傍晚开球的赛事 | 按末场结束后 +1.5h 排 |
| 多场次跨日 | 按**最后一场结束时间**排一次，不要按第一场排多次 |

规则背后的原则：**触发点应当由「数据何时可用」决定，而不是由「我想什么时候看结果」决定。**

## 三、扑空时的处置：负向操作清单

比赛未结束时，以下动作一律不做：

| 动作 | 为什么不能做 |
| --- | --- |
| `settle`（写入赛果） | 没有赛果可写，任何填入都是编造 |
| `export`（刷新看板） | 数据无变化，只会产生无意义的版本 |
| 写 notes / 新增偏差规则 | 没有赛果就没有可核销的预言，写出来的规则无依据 |
| 报「已完成」 | 会掩盖真实状态，导致后续依赖该状态的流程判断错误 |

正确输出是**一份带证据链的「未执行」说明**：每场 ≥2 个独立来源、全部显示未开赛，并附时间换算表。这样下一次执行者（人或程序）不必重新验证。

## 四、搜索旧战报：回填类任务最大的误填源

一次搜索「萨索洛 佛罗伦萨 比分」，返回了 4 条不同赛季的结果（2-1、5-1 等），全部是历史战报。另有一次「Newcastle 2-3 Everton」的报道，日期是 **2026-03-03**，与当轮无关。

### 判定流程

```
搜索命中比分
   ├─ 该源是否明确标注「本场日期 + 开赛/完场状态」？
   │     ├─ 否 → 弃用（无论比分多合理）
   │     └─ 是 → 核对日期与主客顺序
   │            ├─ 一致 → 采纳（仍需第二源交叉）
   │            └─ 不一致 → 弃用
   └─ 无比分、只标「未开赛」 → 记录为「未开赛」证据
```

**关键翻转**：把「有没有比分」换成「该源是否标注本场状态」。前者会被旧战报骗，后者不会。

### 主客顺序陷阱

同一对阵在不同赛季主客互换，比分随之不同。「那不勒斯 2-1 尤文」与「尤文 2-0 那不勒斯」是两场不同的比赛，仅凭队名和比分无法区分，必须核日期。

## 五、回填脚本的三个语义陷阱

在数据回填工具链上踩到的坑，与自动化排期无关，但同属一类：**工具的行为与直觉不符，且失败是静默的。**

### 1. 「导入」会覆盖整场记录，不是合并

某 `import` 子命令会先删除整场的 `forecasts / scores / handicaps` 再写入。若只想补几条 `notes`，走 `import` 会把该场已有的预测数据清空。

**规则**：只改注释/备注类字段时，直接走 `sql` 定点插入，不经过整场导入。整场导入只用于「重建该场」。

**通用做法**：任何「导入/同步」类命令，先看它是 upsert 还是 replace。两者在名称上经常都叫 import。

### 2. 并列值排序会崩溃

`_report_one` 中 `sorted(rows)` 在两条记录 Brier 并列时抛异常——`sqlite3.Row` 之间不可比较。恰好在我与市场同分的那一场触发。

**修复**：`sorted(rows, key=lambda t: t[0])`。

**教训**：排序必须显式给 key。依赖默认比较的实现，在数据出现并列时才会暴露，属于典型的「只在低概率分支上崩」。

### 3. 定时任务提前触发会消耗一次性任务的机会

一次性任务若在计划时间之前被触发（无论因何原因），可能已被标记为已执行，到点不会再跑。

**规则**：发现提前触发后，先核对任务状态；若仍显示 ACTIVE 且计划时间未到，不能假定它还会跑——需要人工确认或改期。

## 六、可复用检查清单

排一个「等待外部数据到位后再执行」的自动化任务时，逐条过：

1. 数据的可用时间点是否已换算到**触发时区**？
2. 触发点是否 ≥ 末个数据源产出时间 + 缓冲？
3. 数据未就绪时，任务是否有明确的「不动作」分支？
4. 验证数据是否就绪，是否用了「状态字段」而非「是否搜到内容」？
5. 写入操作是否幂等？重复执行会不会产生重复记录？
6. 一次性任务的执行机会是否会被提前触发消耗？
7. 失败时是否留下可复用的证据链（来源、时间、判定理由），而不是只留一句「失败」？

## 七、任务 ID 与去重维护（2026-11-06 新增）

事故很小，代价明确：给「11-07 五场核销」任务追加「用户自选两注」段落时，直接引用了记忆里的 id `07e09cbb-…`，返回 `automation id not found`；实际 id 是 `075e9b70-…`（前六位相同，后段完全不同）。

### 三条规则

1. **任何按 id 的操作前先 `list`。** id 是运行期产物，跨会话的手写记忆不可信；`list` 一次即可拿到 name → id 的准确映射，成本远低于一次失败的 `update` 加一轮排查。
2. **同一晚的同类核销只维护一条任务。** 新增核销对象（用户自选注、新设检验场）应当 `update` 既有 prompt 增量追加，不要 `create` 第二条——两条同晚核销任务会在次日各自跑一遍，产生重复结论与重复写库，且两份结论口径容易不一致。
3. **核销任务的 prompt 要连「赛前数值」一起写进去。** 核销的输入不是结论，而是「赛前写下的数字 + 当时的风险点」。本次把模型概率、竞彩去水概率、EV 三个数一并写入 prompt，次日才能分清是预测错还是记录错。

### 判据

> 自动化任务是**持久对象**，不是一次性调用。任何「新建」都应当先回答：同一时点是否已有承担相同职责的任务？如果答案不确定，先 `list`。

这条与第一节的时序陷阱同源：都是「任务的生命周期比这一轮对话长」所带来的问题——一个是时间维度（何时触发），一个是标识维度（改哪一条）。

## 八、自动化「静默未触发」的排障（2026-11-07 新增）

### 事故形态

06:30 的自动核销任务当天没有任何执行日志——自动化**已配置工作目录，但从未被触发**。这与「触发了但报错」是两类完全不同的故障：后者有日志可查、有错误可修；前者在系统里没有留下任何痕迹，只能靠下游（当天该有产出却没有）反向发现。

### 处置流程

1. **先查自动化日志确认「未触发」而非「失败」**——判断故障层级（调度层 vs 执行层）；
2. **手动补做**，不等待下一次自动触发；
3. 补做时赛果按回填纪律执行多源核对：本次用四个独立来源交叉核对一致（纳米数据 + 懂球帝开奖 + 新浪 + 腾讯）后才入库。

### 规则

- **静默未触发 ≠ 执行失败**，排障第一步永远是区分这两类；调度层故障没有错误信息可修，只能靠检查点兜底。
- **涉及数据交付的自动化应在主流程入口设「当日是否已有产出」的检查点**：由人工或下一个环节验证产出存在，缺失即告警——不能假设「自动化配置正确就会执行」。
- 手动补做不影响数据质量的前提是**回填纪律照常执行**（多源核对、日期+进球人+轮次三要素甄别），不因「补做」而降级核对标准。

## 九、核销任务的「过程三件套」与自动化 prompt 升级（2026-11-08 新增）

### 事故：回填被简化成「填个比分」

用户在核对罗马 vs 曼联一役时指出：我把该场定性为「周中欧冠血战 90 分钟」，据此对罗马做体能扣减。实际数据是该队下半场射门 **10-0**、xG **2.48–0.00**——不是血战，是领先 2-0 后主动收缩、放弃比赛管理。

数据层同时给出更硬的证据：罗马是**欧冠史上首支单赛季两次 2 球领先被逆转的球队**（另一场 3-4 皇马，曾 3-1 领先）。这是结构性「守不住领先」，与体能无关。

用户随后指出根因不在 token 成本：「你自己又不是调不出比赛信息」——过程数据一直可得（纳米数据逐分钟事件流、懂球帝/雷速技术统计、赛后战报的下半场拆分），是流程设计里没有这一步。

### 规则：settle 必须带「过程三件套」

| 项 | 取数口径 | 用途 |
| --- | --- | --- |
| 进球时间分布 | 逐分钟事件流 | 判断是崩盘、慢热还是被绝杀 |
| 下半场射门 / xG 拆分 | 战报或技术统计 | 区分「血战」与「松懈」：领先方下半场数据塌陷 = 松懈 |
| 红黄牌与关键换人 | 阵容页 + 事件流 | 判断红牌、被动换人、主动放弃等变量 |

### 规则：引用历史比赛性质前必须先验性质

赛前使用「周中消耗大」「鏖战」「惜败」「血战」这类标签前，必须先查该场比赛的下半场数据，确认性质后才可计入扣减：

- **血战**（全场高强度、双方数据接近）→ 扣体能，作用于 1X2 方向；
- **松懈 / 领先后失去控制**（领先方下半场数据塌陷）→ **不扣体能**，记为「领先管理能力缺陷」，只作用于让球盘（赢 2 球以上的能力），不作用于方向。

这条区分在本轮直接改写了结论：罗马的体能扣减被撤掉，但「让胜别碰」的结论反而更硬——理由从「跑不动」换成「一支两次 2 球领先都守不住的队，赌它净胜 2 球等于赌它做得到它被证伪的事」。

### 自动化 prompt 的同步升级

1. 回填任务每场 settle 强制输出三件套，缺项视为未完成；
2. 已手动结算的场次在任务 prompt 中标注「仅补核销」，避免重复回填；
3. **顺手清理已失效的旧任务**：比赛早已手动结算、任务仍挂着等待触发（如 11-06 水晶宫回填），属于「持久对象的生命周期未收尾」，与第八节的判据同源——新建前先 `list`，完成后核对是否还有同一职责的残留。

### 分工边界（本次确立）

- **过程数据自查 = Agent 的默认职责**，不得以「用户没看球」为由省略；这是输入侧的最低要求，不是可选增值项。
- **用户的过程观察仍是有效补充**：「他们是莫名其妙松掉的，不是跑不动的」这类比赛气质判断，数据存在盲区，应作为一手证据直接用于修正性质定性。
- 但用户观察是**补充**，不是**必要输入**——流程不能建立在「用户每场都看」的假设上。
